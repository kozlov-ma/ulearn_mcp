# Контракты ulearn

Базовые контракты проверены 30 октября 2026 года; баллы за модули, продление токена и единая сессия — 8–9 ноября 2026 года. Источники: текущая [OpenAPI-схема](https://api.ulearn.me/documentation/v1/swagger.json), [Swagger UI](https://api.ulearn.me/documentation/index.html) и опубликованный JavaScript самого ulearn. Наличие маршрута в схеме не заменяет прав преподавателя. Реальные комментарии и оценки для проверки не создавались.

## HTTP и авторизация

API расположен на `https://api.ulearn.me`, сайт — на `https://ulearn.me`. Эти адреса задаются отдельно: маршруты ведомости не являются маршрутами API.

### Единая сессия

- Пользователь импортирует cookie в скрытом вводе `bootstrap-session [SESSION_FILE] [--replace]`. Команда проверяет сессию через обмен токена и `GET /account`, затем атомарно сохраняет только cookie с правами `0600`. MCP не извлекает браузерное хранилище. Путь по умолчанию — `~/.config/ulearn-mcp/ulearn.cookie` с учётом `XDG_CONFIG_HOME`; явная настройка — `ULEARN_SESSION_FILE`.
- `POST /account/token` принимает `Cookie` и возвращает `TokenResponse` с JWT в поле `token`. Cookie не передаётся обычным API-запросам: они используют только `Authorization: Bearer <JWT>`. Полученный JWT проверяется через `GET /account`; используется `user.id` авторизованного аккаунта. JWT остаётся в памяти и не выводится в ответы MCP.
- При первом запросе, отсутствии JWT или достижении времени обновления выполняется новый обмен cookie. Запас до истечения равен `min(300 секунд, половина оставшегося срока при получении JWT)`, что позволяет использовать короткоживущие токены. Для действительной сессии это работает и после истечения прежнего JWT. Срок токена задаётся ulearn; `refresh-token` принудительно повторяет обмен, а `--days` в режиме сессии отклоняется. Запущенные процессы получают собственные JWT.
- Cookie сама не продлевается: `Set-Cookie` не сохраняется, браузерная cookie jar не ведётся. При истечении или отклонении сессии пользователь выполняет `bootstrap-session --replace`. После `401` обычного API-запроса кеш JWT сбрасывается; текущая операция не повторяется, и только следующая получает токен заново. Автоматического повтора исходной операции после ошибки сети или неопределённого результата записи также нет.
- Первый проверенный `user.id` фиксируется на время процесса. Изменение файла cookie сбрасывает кеш JWT, но новая сессия допускается только для того же аккаунта. Другой аккаунт требует перезапуска и повторного чтения контекста. Все операции записи фиксируют сессию и JWT на весь цикл проверки, отправки и сверки; замена файла в середине операции не переключает автора и блокирует последующую запись.
- `set_module_score` требует режим сессии. Он использует ту же cookie, из которой получен JWT проверки; отдельного источника авторизации для ведомости нет. Для собственного сервера нужны явные `ULEARN_API_URL`, `ULEARN_WEB_URL` и путь сессии. Стандартная cookie автоматически подхватывается только для стандартной пары адресов.
- `config --session` формирует JSON без секретов. Для миграции нужно заменить старую запись MCP и перезапустить подключение: явные `ULEARN_TOKEN_FILE`/`ULEARN_TOKEN` имеют приоритет над файлом сессии по умолчанию. Явная сессия одновременно с явным токеном отклоняется.

Разделение cookie-only `/account/token` и instructor `/account/api-token` подтверждено [историческим исходным кодом AccountController](https://github.com/vvadik/Ulearn/blob/master/src/Web.Api/Controllers/AccountController.cs); текущая [Swagger-схема](https://api.ulearn.me/documentation/v1/swagger.json) содержит маршруты и `TokenResponse`. Проверки авторизации используют локальные подставные серверы; успешный обмен реальной cookie в рамках разработки не проверялся.

### Совместимость с отдельным JWT

- `bootstrap [TOKEN_FILE] [--replace]` сохраняет введённый JWT после `GET /account`; автоматическое продление на этой проверке отключено. Источник — `ULEARN_TOKEN_FILE`, `ULEARN_TOKEN` либо прежний файл по умолчанию, если сессия не выбрана. Одновременно задавать `ULEARN_TOKEN` и `ULEARN_TOKEN_FILE` нельзя.
- `POST /account/login`, JSON `{login,password}` → ответ с `token`. Команда `login TOKEN_FILE` сохраняет только JWT; вход через внешний провайдер этим контрактом не подтверждён.
- `POST /account/api-token?days=N` с действующим Bearer выдаёт токен только преподавателю. MCP использует 30 дней по умолчанию, допускает 1–365 (`ULEARN_TOKEN_REFRESH_DAYS`); автоматическое продление выполняется при остатке не более пяти минут и отключается `ULEARN_AUTO_REFRESH_TOKEN=false`. При отказе обновления `403` ещё действующий токен остаётся доступен для разрешённых операций.
- `refresh-token [--days N]` в этом режиме требует файл токена. Файл перечитывается перед запросами и заменяется атомарно; обновление `ULEARN_TOKEN` остаётся в памяти процесса. Отдельного refresh token/grant нет: истёкший самостоятельный JWT требует `bootstrap --replace`.
- `GET /account` и `GET /account/roles` возвращают личность и роли. Токен не расширяет права аккаунта. JWT `exp` читается локально для планирования; подлинность подтверждает сервер. Использование Bearer подтверждено также [официальной интеграцией ulearn](https://github.com/kontur-edu/ulearn-scripts/blob/master/src/apis/ulearnApi.ts).

## Чтение

| Маршрут | Параметры и существенные поля |
| --- | --- |
| `GET /courses` | Каталог курсов. |
| `GET /courses/{courseId}` | Необязательный `groupId`; `units[].slides[]`, идентификаторы и настройки оценивания. |
| `GET /slides/{courseId}/{slideId}` | Упорядоченные полиморфные `blocks[]`; HTML, код, упражнение и другие типы содержимого. |
| `GET /groups` | `courseId`, `offset`, `count`. |
| `GET /groups/{groupId}/students` | Состав группы. |
| `GET /review-queue` | Обязательный `courseId`; `studentsFilter`, повторяющиеся `groupIds`, `studentIds`, `slideIds`, `sort`, `count`. Результат: `checkings[]`. |
| `GET /review-queue/history` | Те же фильтры плюс `minTimestamp`. |
| `POST /user-progress/{courseId}` | Чтение, несмотря на POST: JSON `{userIds:[userId]}` → `userProgress[userId].visitedSlides` и `additionalScores[unitId][scoringGroupId]`. |
| `GET /submissions` | `courseId`, `slideId`, `userId`; результат `{submissions,prohibitFurtherManualChecking}`. |

Значения `studentsFilter` в интерфейсе: `all`, `mygroups`, `groupids`, `studentids`; `sort`: `ascending`, `descending`. Элемент очереди содержит `submissionId`, `slideId`, `user`, `timestamp`, `score`, `maxScore`, `lockedBy`, `lockedUntil`, `checkedBy`, `checkedTimestamp`, `reviews`.

У попытки используются `id`, `code`, `timestamp`, `automaticChecking`, `manualChecking`. Комментарии находятся в `manualChecking.reviews`, автоматические замечания — в `automaticChecking.reviews`. Текст замечания в ответе называется `comment`; ответы в ветке — `comments[].text`. Оценка — `manualChecking.percent`.

Это подтверждено [адаптером запросов](https://ulearn.me/static/js/main-d91a9049.ac4a7437.js), [состоянием приложения и перечислениями](https://ulearn.me/static/js/main-84781932.efb27901.js) и [интерфейсом ревью](https://ulearn.me/static/js/main-31743c5a.dc2e46fd.js). Ссылки на файлы сборки могут измениться при обновлении сайта.

## Запись

Порядок работы агента задан в [ulearn-review](skills/ulearn-review/SKILL.md): сначала показать конкретный черновик комментариев/ответов и оценки, затем дождаться отдельного явного согласия пользователя, затем публиковать только согласованные действия. Тело этого skill встроено в `initialize.instructions` MCP, а описания инструментов записи повторяют требование согласия. Подтверждение проверяет агент; MCP-сервер не читает переписку и не может технически удостоверить ответ пользователя. Проверки хеша/оценки защищают от устаревшего состояния, но не заменяют согласие.

| Маршрут | Тело / параметры | Значение |
| --- | --- | --- |
| `POST /reviews?submissionId={id}` | JSON `{text,startLine,startPosition,finishLine,finishPosition}` | Новый комментарий к исходному коду. |
| `POST /reviews/{reviewId}/comments` | JSON `{text}` | Ответ в существующей ветке ревью. |
| `POST /submissions/{id}/score?percent={n}` | Целый процент | Выставление оценки за ревью данной попытки. |
| `POST https://ulearn.me/Admin/SetAdditionalScore` | Query `courseId`, `unitId`, `userId`, `scoringGroupId`; form `score` | Дополнительные баллы выбранной категории модуля; авторизация общей cookie сессии. |

Диапазоны напрямую передаются в CodeMirror как `line`/`ch`: нумерация с нуля, колонки в UTF-16. Максимальная длина текста — 10 000 UTF-16 единиц. Успешные POST ревью могут возвращать пустое тело; схема не описывает все ответы, поэтому API-клиент сохраняет произвольный JSON. Для обработчика дополнительных баллов проверяется отдельный документированный ответ, описанный ниже.

В интерфейсе оценки — 0, 25, 50, 75, 100%. MCP допускает целые проценты 0–100; принятие промежуточных значений производственным сервером отдельно не проверялось. Непустое `manualChecking.percent` в интерфейсе даёт статус «прошло код-ревью».

`POST /submissions/{id}/manual-checking` означает **возобновление** ревью, а не завершение; MCP его не вызывает. Разрешение будущих ревью меняет отдельный `PUT /user-progress/{courseId}/{slideId}/prohibit-further-manual-checking?userId=…&prohibit=…`; выставление оценки через MCP этого не делает.

Интерфейс обрабатывает отказ записи `has_newest_submission` с идентификатором новой попытки. MCP не заменяет выбранную попытку новой; при HTTP-ошибке клиент возвращает статус и не раскрывает произвольное тело ответа. Для восстановления нужно перечитать попытки. Гарантии атомарной проверки версии, транзакции для нескольких комментариев и ключа идемпотентности в опубликованном контракте отсутствуют.

## Баллы за модуль и активность

`get_module_scores` объединяет `GET /courses/{courseId}` (необязательный `groupId`) и `POST /user-progress/{courseId}` для одного точного студента. Структура прогресса подтверждена [официальными скриптами интеграции](https://github.com/kontur-edu/ulearn-scripts/blob/master/src/apis/ulearnApi.ts). `units[].additionalScores[]` задаёт `id`, `canInstructorSetAdditionalScore`, `maxAdditionalScore`; `slides[]` — `scoringGroup` и `maxScore`.

Результат содержит по каждой категории `slide_score`, `additional_score`, `score` (их сумму), `slide_max_score`, `max_additional_score`, `max_score` и метаданные. Пустая дополнительная оценка остаётся `null`, а ноль — числом. Отсутствие записи студента в `userProgress` — ошибка, не нулевой результат. Показываются только видимые модули; веса категорий и правила итоговой оценки не применяются автоматически.

`set_module_score` принимает точные `course_id`, `unit_id`, `user_id`, `scoring_group_id`, обязательные nullable-поля `score` и `expected_score`, необязательный `group_id`. Меняется только дополнительный балл категории. `score: null` очищает значение; `score: 0` записывает ноль. Прежнее отсутствие оценки передаётся как `expected_score: null`.

Запись выполняется через обработчик сайта `POST /Admin/SetAdditionalScore?courseId=…&unitId=…&userId=…&scoringGroupId=…`, `Content-Type: application/x-www-form-urlencoded`, поле `score`. Целое значение `0..maxAdditionalScore` устанавливает балл, пустая строка очищает. Ожидается JSON `{status:"ok",score:<число или "">}`; клиент возвращает только эти поля. Маршрут, параметры, диапазон и очистка подтверждены [историческим AdminController](https://github.com/FireFenixKZ/Ulearn/blob/master/src/uLearn.Web.Core/Controllers/AdminController.cs) и [UnitSheet](https://github.com/FireFenixKZ/Ulearn/blob/master/src/uLearn.Web.Core/Views/Analytics/UnitSheet.cshtml); текущий [JavaScript сайта](https://ulearn.me/static/js/main-84781932.efb27901.js) отправляет форму `{score:…}` по адресу поля ведомости.

До записи читаются актуальные данные точного студента и модуля: проверяются категория, `canInstructorSetAdditionalScore`, максимум и равенство `expected_score`. Неизменившееся значение возвращается как подтверждённая операция без записи. Весь цикл выполняется с одним снимком общей сессии; непосредственно перед POST проверяется, что файл сессии не заменён. После принятой записи прогресс перечитывается через API. `write_accepted: true` и `score_verified: false` означают, что запись принята, но её результат не подтверждён; автоматически повторять её нельзя.

В Swagger нет эквивалентного Bearer-метода изменения дополнительных баллов. `POST /groups/{groupId}/scores` настраивает доступные категории группы, а `POST /submissions/{id}/score` оценивает конкретную попытку. Они не заменяют запись баллов модуля. Успешный сценарий с реальной cookie и изменение реальных баллов не проверялись; контракты покрыты подставными API и сайтом.

## Что нельзя заключать из схемы

- `SubmissionInfo` в Swagger пуст, `ReviewInfo` почти пуст. Декодирование в строгую сгенерированную модель могло бы потерять исходники и отзывы; здесь сохраняется JSON.
- В Swagger перечисления часто числовые, фактический интерфейс использует строковые значения. Полиморфные блоки также нельзя свести только к тексту.
- Для очереди нет документированного offset/cursor, для истории не подтверждена полнота обхода по времени. Ограниченная очередь не равна всем решениям курса.
- Отдельного `GET /submissions/{id}` нет. Для точной попытки нужны курс, задача и студент; затем выбирается ровно совпадающий ID.
- Возвращённые права и видимость зависят от аккаунта и группы. Отсутствие данных не доказывает, что студент ничего не сдавал.
- Проверка хеша и предыдущей оценки перед записью уменьшает риск устаревшего контекста, но между чтением и POST другой преподаватель может изменить состояние.
- Таймаут или ошибка чтения после POST не доказывают отмену записи. Публикации автоматически не повторяются; требуется чтение для сверки.

Сервер не выполняет студенческий код, не скачивает внешние архивы и не обходит ограничения доступа ulearn.


## Страница токена для прежнего режима

Страница https://ulearn.me/token подтверждена по [production bundle token](https://ulearn.me/static/js/token.0cc926b2.chunk.js), модуль 971. Название — «Токен доступа», кнопка — «Скопировать токен». Страница показывает текущий JWT; при отсутствии токена у авторизованного пользователя обновляет его через POST /account/token с cookie. Срок действия в интерфейсе не указан. Команда `bootstrap` не открывает страницу: пользователь копирует JWT сам, вводит его скрыто в терминале; программа проверяет GET /account и сохраняет файл токена. Основная команда `bootstrap-session` импортирует cookie отдельно и описана выше. Получение токена в реальном аккаунте в ходе разработки не выполнялось.
